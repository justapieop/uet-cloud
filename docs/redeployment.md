# Rebuild and update a deployment

`POST /deployments/:id/redeploy` queues a rebuild and image update for an existing deployment owned by the signed-in user. Send `Idempotency-Key` and no body (or `{}`). The response is HTTP 202 with the accepted deployment snapshot, `PENDING`, the same deployment ID/resource ID, and a cleared build ID. Poll `GET /deployments/:id`; its new build ID appears after build acceptance. `GET /deployment/build/:id` retains its existing owner-scoped authorization.

The route requires an active, unsuspended session and `DeploymentUpdate`. It rejects foreign/missing IDs with 404 before Stripe/Azure work. It verifies active Stripe membership outside SQL transactions, then locks the user inside the UnitOfWork, checks a single active plan covers the saved per-deployment resources and current reservation count, and saves the queue transition and durable acceptance receipt together. Redeploying does not insert a new deployment or consume another deployment slot. Accepted retries return their original receipt without another build or Stripe call, after current authorization checks.

Only `RUNNING` deployments, or `FAILED` deployments retaining an Azure resource, can redeploy. A saved creation specification and existing resource ID are required. Stopped, deleted, unprovisioned, pending, provisioning, starting, and stopping deployments return 409. Nonempty bodies and invalid UUIDs/keys return 400; missing billing eligibility returns 403; quota conflicts return 409; unavailable Stripe checks return 503. HTTP idempotency conflicts retain the existing 409/422 behavior. The endpoint does not accept another owner's resource ID, a different repository/ref, or cloud configuration changes.

The existing database worker claims the queued row as `PROVISIONING`. It resolves the original saved Git reference again (or HEAD when none was provided), authorizes repository access, and schedules the existing Azure Pipeline. A saved immutable commit reference rebuilds that commit; a branch resolves its current commit. Images remain `<registry>/<imageName>:<fullCommitSha>`.

The shared `infra/azure/pipelines/build.yml` continues building and pushing only. After it reports `SUCCEEDED`, Kumo re-reads the target app, verifies the stored subscription/user RG/name/resource ID, deployment tag, and managed environment, and updates the main-container image through ACA's PATCH operation. It preserves the current template's other containers, environment variables, resource limits, scaling, probes, and volumes, and omits app-level ingress, identities, and secrets from the update. It does not retrieve secret values or replace configuration with the old creation request. A deterministic build-ID revision suffix ensures a distinct revision even when rebuilding the same source commit. Initial provisioning continues using create-or-update and creates the app only after build success.

Missing existing apps/environments are not recreated by redeploy. Failed/canceled builds never submit an image update. On success, SQL records the new build/image and `RUNNING`. On failure it records the latest workflow attempt as `FAILED` with a safe error, retaining the existing resource ID; an older Azure revision can still be serving. Inspect the build and Azure revision when diagnosing failure. Azure provisioning success is not an independent application-health guarantee. A cloud write can have succeeded despite a lost response; stale provisioning still fails after the existing timeout plus one minute and is not automatically resubmitted.

Conditional owner-scoped SQL status transitions serialize redeploy acceptance against competing stop requests. Lifecycle handlers claim `STARTING` or `STOPPING` before cloud calls and conditionally complete their transition afterward. Those transient states reserve deployment quota and appear in list/detail responses and filters. Known operation failures attempt to restore the prior lifecycle state. A process crash can leave a lifecycle transition unresolved; operators must inspect Azure and reconcile it. This is not a durable lifecycle recovery service, and out-of-band Azure changes are not fenced by SQL.

No migration or new `.env`/pipeline variables are required: queue status and resource IDs already exist in SQL, and the backend's existing ARM identity performs the update. It needs Container App update permission, as it already does for provisioning. The build pipeline service connection retains its ACR push scope; no fixed app names/resource groups are added to it.

This adds rebuild/update through Kumo, not a GitHub-push webhook. A frontend button or API caller initiates redeployment. Repository push subscriptions and webhook signature/replay validation remain separate future work.

Validation: `npm run test:api` includes application receipt/eligibility/rollback tests, HTTP permission and replay tests, Azure ownership/build-gating/configuration-preservation tests, and lifecycle tests. The separate `npm run test:db` suite includes competing redeploy/stop status transitions on real SQL Server; run it only with dedicated test credentials. Neither suite deploys to live Azure.
