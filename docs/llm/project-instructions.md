# Project instructions for LLMs

## Project

This project is building a cloud-integrated Platform as a Service (PaaS) for developers and platform-oriented teams, including DevOps and MLOps practitioners. The platform enables users to deploy applications using Azure Container Apps (ACA).

The platform itself is intended to be hosted on Azure. Organize its code using Clean Architecture to support clear boundaries and future growth.

The codebase is an npm workspaces monorepo with `apps/api` as a thin NestJS server entry point and `apps/web` as the frontend client. NestJS bootstrap and module composition live in `packages/presentation`. `packages/domain`, `packages/application`, `packages/infrastructure`, and `packages/presentation` hold the Clean Architecture boundaries. `packages/contracts` and `infra/azure` are reserved for shared contracts and Azure deployment configuration. The frontend technology remains an open decision.

Organize the frontend within `apps/web` using [Feature-Sliced Design](https://fsd.how/). Follow its layer dependency and slice boundaries, and expose slices through public APIs. Add only layers and slices that serve implemented functionality; the frontend framework remains undecided. This frontend structure applies within `apps/web` and does not replace the backend package boundaries above.

Keep use cases under `packages/application/src/use-cases`. Group related code by feature within each package as features are defined. Domain code must not depend on NestJS or Azure SDKs; the application package depends inward on domain concepts, while infrastructure and presentation implement outside adapters. Define infrastructure modules as `@Module` classes alongside their providers in `packages/infrastructure`; compose them in the presentation root module and invoke the presentation bootstrap from `apps/api`.

Define `BuildModule` in `packages/presentation/src/modules/Build.module.ts`, where it wires build use cases to infrastructure providers. Build providers, repositories, and the worker remain in `packages/infrastructure` and are exported through its public API.

Keep Container App start/stop in the infrastructure `AzureContainerLifecycleManager`, separate from provisioning/build orchestration in `AzureProvider`. Share workload resource-group and ARM identity validation through `azure/workload-scope.ts`. See `architecture-review.md` for current boundaries and unresolved rename/deletion/reconciliation gaps.

For use cases that require multiple database writes to succeed or fail together, use the application-layer `UnitOfWork` port. Its infrastructure implementation supplies repositories bound to one TypeORM transaction; perform all writes through those repositories within the unit-of-work callback. When composing operations, the outer use case owns the transaction and passes those repositories to inner operations; inner operations must not open another unit of work.

Every domain definition in `@kumo/domain` must extend the `Domain<TDetails>` base class exported from `src/domain.ts` through `src/index.ts`. Each concrete domain must expose one public constructor argument named `details`, typed by its corresponding `*Details` interface, and pass it to `super(details)`. The base class stores the details and calls `validate()` during construction, so validation must read stored details rather than subclass fields initialized after `super()` returns. `validate()` returns `InvalidDomainParams` for invalid construction data and `null` when valid. `InvalidStateTransition` is reserved for state validation and transition failures; its behavior is not yet implemented. Keep imports acyclic: domain files import the base from `src/domain.ts`, while `src/index.ts` re-exports the base and concrete domains.

Permission definitions and the permission catalog live in `packages/domain/src/permission.ts`; the role domain imports them from that file. Each permission definition must include a stable zero-based `offset`, `name`, `description`, and a readonly `requires` array of prerequisite permission definitions. The prerequisite field currently records dependencies; enforcement is not yet implemented. Compute its mask as `1n << BigInt(offset)` when needed; do not store a precomputed mask or reuse/renumber an assigned offset. `Role.hasPermission()` grants any requested permission when the role has the `Super` bit, otherwise it checks the requested permission's bit. `Role.getGrantedPermissions()` returns known definitions granted by the role, and a role with `Super` receives every definition in the catalog. `Role.getStoredPermissions()` reports exact catalog bits stored on the role without expanding `Super`; use it for administration views. Metadata does not control access. Unknown stored bits have no catalog entry and are omitted. Resource or tenant scope checks are separate and are not specified here.

Use `@RequirePermissions(...permissions)` on permission-protected controllers or methods. Its guard requires an authenticated, active, unsuspended user. Session deserialization loads the current user and active assigned-role bitsets in one joined SQL query per request. The guard uses the resulting non-enumerable request-local mask, with `CheckPermissionsCase` as the fresh role-lookup fallback. Both paths require every requested bit; an active role's Super bit grants every valid requested permission. Controller and method requirements are additive. Role activity defaults to true. Role lookups must be owner-scoped and must not cache grants, so assignment/activity changes take effect on the next request. The global `PermissionsModule` wires the guard and use case in the presentation root. Keep resource ownership checks separate. See `../permissions.md` for usage.

For Azure Container Apps and ARM SDK interactions in `@kumo/infrastructure`:
- For `@azure/arm-appcontainers`, new app/environment provisioning uses `.createOrUpdate(resourceGroupName, appName, envelope).pollUntilDone()`. Image-only redeployment of an existing owned app uses `.update(...).pollUntilDone()` with a template/tags PATCH that omits configuration, identities, and secret values. Never invoke deprecated methods such as `beginCreateOrUpdateAndWait()`, `beginCreateOrUpdate()`, or `beginUpdateAndWait()`.
- Azure Container App names must be validated against `^[a-z][a-z0-9-]{0,30}[a-z0-9]$` (2-32 characters, lowercase alphanumeric and hyphens, starting with a letter and ending with an alphanumeric character).
- User isolation: All user workloads belong to `user-rg-<userId>`. Guard against any deployment or RG modification targeting the central system RG.
- Each user has one managed environment named `user-aca-env-<userId>`, shared by that user's Container Apps. For a missing environment, create/reuse `user-vnet-<userId>` in the same `user-rg-<userId>` and normalized region first, with a dedicated `aca-infrastructure` subnet delegated to `Microsoft.App/environments`. New networks use `10.0.0.0/16` and a `10.0.0.0/24` subnet. Await network/subnet readiness before creating the Workload Profiles environment with `vnetConfiguration.infrastructureSubnetId` and `internal: false`, then await environment readiness before building. Preserve existing environments and network configuration; reject incompatible networks rather than overwriting them. See `../user-networking.md`.
- New managed environments must explicitly set `environmentMode: "WorkloadProfiles"` and configure the `Consumption` workload profile. Container Apps select that consumption profile. Reject an existing Express environment before building, because it does not support the required configuration surface. Do not delete or replace an existing environment automatically.
- Users may supply optional `region` in deployment creation as a lowercase Azure location name, such as `japaneast`. Persist it in the creation specification and return the requested region in pending/mutation responses (null when omitted); provisioned detail/list GETs return the applied Azure region. Use it for new user resource groups and managed environments, including new environments in an existing resource group. Without it, new groups default to `southeastasia` and new environments use their group's location. Existing shared environments must match an explicitly requested region; otherwise fail before starting a build. Do not assume a region is permitted by the subscription or silently recreate an existing environment to change regions. Region selection is a request field, not a global configuration setting.
- Normalize Azure-returned locations by removing whitespace and lowercasing before comparison or reuse in resource creation. For example, `Japan East` and `japaneast` must match.
- Deployment/build clients do not supply image tags. Resolve the requested Git reference to its full 40-character commit SHA, normalize it to lowercase, and persist `<registry>/<imageName>:<commitSha>` with the commit before scheduling the pipeline. Pending builds store the untagged repository address until resolution. The image name defaults to the app name; no user namespace is added. Build UUIDs remain separate tracking/source authorization identities. The pipeline validates both the assigned `build_id` and that its image tag equals manifest `commit_sha`. Rebuilds of the same name/commit reuse the same tag. Legacy queued tag values are replaced during preparation; do not rewrite historical deployed image references.
- `AzureProvider.createDeployment()` reuses existing apps, otherwise runs the existing GitHub/Azure Pipelines build flow and waits for `SUCCEEDED` before creating the Container App. Build failure, cancellation, or deployment timeout must prevent app creation. Use `.pollUntilDone()` for new managed environments and Container Apps. Permission or other Azure errors must propagate; only a 404 means a resource is missing.
- ACR images must remain private. Check that the configured registry has anonymous pull explicitly disabled before starting a build. Kumo authenticates ARM calls through `DefaultAzureCredential`; configure the Container App with an existing user-assigned identity that has ACR pull access. Accept its name through `AZURE_CONTAINER_REGISTRY_PULL_IDENTITY_NAME` and construct its resource ID from `AZURE_SUBSCRIPTION_ID` and the platform resource group (`AZURE_PLATFORM_RESOURCE_GROUP`, falling back to `AZURE_RG_NAME`). Set that identity's lifecycle to `None` so tenant application code cannot obtain tokens for the pull identity. Do not use registry passwords or persist temporary Azure access tokens as app secrets.
- Presentation controllers for deployment mutation (`POST /deployments`, `PATCH /deployments/:id`) must return `HttpStatus.ACCEPTED` (HTTP 202) representing accepted asynchronous processing.
- Deployment creation requires `max_vcpu`, `max_memory` (GiB), `min_scaling`, and `max_scaling`. Enforce a strict vCPU:memory ratio of 1:2: `max_memory === max_vcpu * 2`. These are per-replica allocations; vCPU uses positive increments of 0.25. Replica counts are integers with `0 <= min_scaling <= max_scaling` and `max_scaling >= 1`. Validate before persisting a creation request and again at the Azure resource boundary.
- Deployment creation accepts top-level `external` (boolean, optional, default true). Persist it with the creation request, apply it to ACA ingress, and expose it in deployment responses. False limits ingress to other apps in the same environment. Reject external additional TCP ports on an internal container before persistence and again at the Azure boundary. Provisioned GETs read applied visibility from Azure (null if absent); legacy queued inputs without the field default to external ingress. No new database column is needed.
- Keep `target_port` for the main HTTPS ingress and accept optional `additional_ports` with up to five TCP mappings (`target_port`, optional `exposed_port` defaulting to target, optional `external` defaulting to false). Persist camelCase mappings in the creation specification, return normalized mappings in deployment responses, and apply them through ACA `additionalPortMappings`. Validate unique additional target/exposed ports, different targets from the main target, range 1–65535, and reserved port 36985. External mappings cannot expose ports 80/443 and require an existing VNet-connected managed environment; fail before building if that prerequisite is absent. Azure enforces exposed external port uniqueness across the environment. New environments receive the user VNet automatically. Existing environments without VNet integration require separate migration before external TCP ports can be used.
- `POST /deployments` persists a `PENDING` request and returns HTTP 202. The database-backed deployment worker claims it as `PROVISIONING`, prepares user resources, builds first, and deploys that successful build's image. Persist its build ID and image while waiting, then its Azure resource ID and FQDN on success (`RUNNING`), or a safe error (`FAILED`). Owner-scoped `GET /deployments` and `GET /deployments/:id` expose progress. Do not hold database transactions across cloud operations. Pending requests survive restarts; provisioning interrupted beyond the configured timeout plus one minute is marked failed and is not automatically retried.

Do not write anything into README.md until told to do so.

Deployment names are globally unique across users, enforced by the database's unique index on `deployments.name`. Let the database arbitrate concurrent name claims and translate duplicate-name errors into a conflict; do not rely on per-user checks for uniqueness.

Before accepting a new deployment, query Stripe for the linked customer's subscriptions with status `active`, including all subscription and item pages. Match product IDs to active local plans. Perform Stripe calls outside the UnitOfWork. Then serialize acceptance for the user with `users.findByIdForUpdate()` inside the acceptance UoW, recheck eligibility of the user and customer association, read current deployments, check quotas, and persist the deployment and idempotency receipt together. CPU/RAM are per-deployment per-replica limits; `max_scaling` must not exceed the plan's `max_replicas`. Count PENDING, PROVISIONING, RUNNING, and FAILED deployments retaining an Azure resource ID against deployment slots. Accepted idempotent retries replay the original receipt without querying Stripe or consuming another slot, after authentication/suspension checks. Subscription verification failures fail closed with HTTP 503; missing eligible subscriptions use 403 and quota failures use 409. Do not implement subscription registration as part of this admission gate.

Each plan may have one unique nullable `stripe_product_id`; unmapped or inactive plans grant no deployment access. Existing rows start unmapped and default to one maximum replica, so configure both fields before enabling them for subscribers. If several subscribed products map to plans, one plan must cover every quota dimension independently; do not stack subscriptions or mix plan limits. Storage enforcement belongs to the future storage-allocation flow.

## Working guidance

- Redeploy uses the existing deployment row/queue with its retained resource ID; it does not allocate another deployment or overwrite creation JSON. Accept only provisioned RUNNING or failed-with-resource deployments. Save acceptance receipts and queue updates atomically in the user-locked UoW, after external Stripe verification. Use conditional owner/status transitions to arbitrate redeploy versus lifecycle commands; STARTING/STOPPING reserve quota and block redeploy. After successful build/push, verify ownership and the environment again and PATCH only the live app template image plus revision/build metadata. Do not add a globally configured deployment target to the shared build pipeline. See `../redeployment.md` for failure and recovery limits.

- Region discovery uses `GET /regions` with an active, unsuspended session and no deployment permission requirement. Use the configured `AZURE_SUBSCRIPTION_ID` and injected credential/HTTP transport; never accept a subscription selector. Intersect subscription locations with advertised `Microsoft.App/containerApps`, `Microsoft.App/managedEnvironments`, and `Microsoft.Network/virtualNetworks` locations. Normalize and deduplicate canonical names, follow validated subscription-local pagination, omit logical/extended locations, and fail with sanitized 503 errors on Azure failures. Also intersect with the live `sys.regionrestriction` assignment's `listOfAllowedLocations`; only a 404 or `DoNotEnforce` skips this filter. Policy read failures and malformed parameters fail closed. After policy/support filtering, read regional Microsoft.App usages and hide regions with ManagedEnvironmentCount.currentValue >= limit. Bound concurrency to five and validate same-region pagination. Missing or malformed quota counters and lookup failures fail closed. Full regions are hidden even for users with an existing environment. Keep quota/other-policy/capacity and existing-environment region checks in deployment provisioning. See `../regions.md`.

- Installed GitHub repository listing uses only the session user's immutable GitHub ID. Resolve and validate the account, verify the personal installation's owner ID before minting a metadata-read token, and filter every repository by the same owner ID. Do not enumerate global installations or accept an account/installation selector. Organization and collaborator-owned repositories are outside this endpoint's scope. Keep credentials backend-only, paginate GitHub results, and fail closed on upstream failures. See `../github-repositories.md`.

- Billing management uses the existing `/plans` and `/user/:userId/subscriptions` routes, with method-level permissions; there is no separate admin route prefix. Public `GET /plans` remains unchanged; `GET /plans/all` lists all local plans with PlanManage. Register `/plans/me` before the dynamic `/plans/:id` route. Management operations are protected by PlanManage (offset 7) and SubscriptionManage (offset 8). Plan writes update local metadata/quotas only; DELETE deactivates. Resolve subscription customers through the persisted target user and verify Stripe subscription ownership before mutation. Only period-end cancellation and undo are exposed; preserve price/meter items. Require owner/operator-scoped Stripe idempotency keys and keep external calls outside transactions. See `../admin-billing.md`.

- Role administration uses `/roles` and `/user/:userId/roles` with RoleManage (offset 9); there is no separate admin route prefix. `GET /roles` returns every role, including inactive roles, with exact stored permission keys plus the static permission catalog. Do not expand Super into individual grants or infer prerequisites from the catalog. Role writes replace the exact permission set, preserve unknown stored bits, and deactivate rather than delete. Assignment writes replace the user's exact active role set. Non-Super actors cannot grant or remove bits they do not hold, and no actor may remove their own resulting RoleManage access. See `../permissions.md`.

- Reduce background database load with adaptive empty-queue backoff (up to ten seconds with jitter), minute stale-work sweeps, and atomic ordered SQL `UPDATE … OUTPUT` claims. Use explicit inserts and targeted progress updates; preserve durable request JSON. Count quota reservations in SQL inside the existing locked UoW. Skip unchanged build-status writes and coalesce in-flight owner-scoped refreshes. See `../database-load.md` for cache TTLs, fresh authorization, and transaction guarantees.

- Deployment detail/list GETs use Azure for applied CPU/RAM, scaling, ports, region, image, and FQDN once an Azure resource ID exists. Keep saved creation inputs for queuing and quota reservations, and keep workflow identity/status/errors in SQL. Use an injected application reader port and an infrastructure Azure adapter; check ownership before Azure access, validate the ARM resource and deployment tag, and never overwrite the saved request with live values. Azure failures must not silently fall back to request snapshots. See `../deployment-configuration.md` for pending/deleted records, filtering, caching, and error semantics.

- Database maintenance scripts must run independently with the API server stopped. Use `build:db` and a standalone TypeORM connection; never bootstrap Nest, load the presentation root, start workers, or depend on an API HTTP endpoint for these commands.

- Backend validation uses `npm run test:api` (API compilation, test type-checking, Node tests, and Python pipeline tests). Run `npm run test:db` separately with dedicated `TEST_SQLSERVER_*` settings for real SQL Server integration. See `../testing.md`. Frontend tests remain deferred. Keep fixtures aligned with current ports, assert specific validation failures, and use the SQL suite for claims about database concurrency or transactional guarantees.

- API response serialization uses the global NestJS `ClassSerializerInterceptor` registered in the presentation bootstrap. Return response DTO instances so `class-transformer` decorators such as `@Expose` and `@Exclude` apply. Do not register the same interceptor again on individual controllers or routes. Plain objects need an explicit DTO type through `@SerializeOptions({ type: ResponseDto })` to use that DTO's decorators.
- Keep OpenAPI security schemes in presentation's `common/OpenApi.ts`. Session-protected operations use `ApiCookieAuth("session")`, backed by `connect.sid`; pipeline source operations use the separate build-source bearer scheme. GitHub OAuth is the login redirect flow, not the session API's bearer authentication. Keep documented success codes aligned with actual HTTP status and regenerate `packages/rest/src/schema.ts` after contract changes.
- Plan subscription registration is a separate authenticated endpoint, `POST /plans/:id/subscriptions`, not part of deployment creation. Accept only the plan ID in the URL, with no body or an empty object; reject client-supplied prices and other fields. Resolve the customer from the persisted user and include every active price on the active plan product, following all price-list pages. Include licensed recurring and one-time prices at quantity one; omit quantity for metered recurring prices. Require at least one recurring price and fail closed on invalid configuration or Checkout limits (20 recurring and 20 one-time); never silently truncate. Sort/deduplicate prices by ID for stable retries. The default price does not restrict selection, and clients cannot pick a subset. Keep Stripe calls outside transactions, scope native Stripe idempotency by user, create a hosted Checkout Session in subscription mode and return only its session ID and URL with no-store, and derive success/cancel URLs from server-controlled FRONTEND_URL, and never grant deployment access based on registration or a browser redirect alone. See `../plan-subscriptions.md` for retry limits and intentionally separate billing features.
- API response caching is opt-in through `CacheRead` and `UserReadCacheInterceptor` in presentation. Deployment list/detail and build-status reads use a two-second Redis TTL for active work, ten seconds for running/stopped deployments, and thirty seconds for terminal builds, with keys scoped by authenticated user, route, and query. Cache only exposed response data; Redis does not preserve DTO prototypes. Preserve authentication and suspended-user checks, leave auth/profile/build-source endpoints uncached, and retain `private, no-store` HTTP policy on authenticated reads. Deployment mutations must invalidate that user's deployment cache generation. Worker updates rely on the bounded TTL; internal build polling remains uncached. Request cache-bypass directives must be honored.
- Explicitly annotate every TypeScript variable declaration (`const`, `let`, or `var`), including exported constants. Do not rely on type inference for variables or use `any` as a substitute for a meaningful type.
- API proxy trust is explicitly configured through `TRUST_PROXY_HOPS` (default zero). HTTPS-terminating ingress requires the appropriate trusted hop count before session middleware so production Secure cookies can be issued. Keep cookie security enabled; validate forwarding-header handling and browser cookie scope when changing the deployment topology. See `../configuration.md#https-ingress-and-session-cookies`.
- Browser login and GitHub installation links use the frontend `/api/auth/*` proxy. Keep its GET allowlist limited to login, callback, and GitHub installation; preserve query strings, upstream redirects without following them, and separate Set-Cookie headers. Use server-configured runtime API_URL, leave the session cookie host-only, and configure OAuth callbacks on the frontend origin. Do not proxy arbitrary API paths or derive upstream hosts from user input. See `../configuration.md#frontend-authentication-proxy`.
- Keep external dependencies used by `packages/infrastructure` and `packages/presentation` in the root `package.json`. Those workspaces declare only their `@kumo/*` package dependencies; the root lockfile records the resolved versions.
- Keep database migration implementations and the typed `DATABASE_MIGRATIONS` registration list together in `packages/infrastructure/src/db/migrations.ts`. The presentation database module uses that list directly. Preserve historical migration class names and ordering so existing TypeORM migration history remains valid; append future migrations to this file and list.
- Keep product intent, architectural choices, and implementation details distinct. Do not present an idea or assumption as a confirmed decision.
- Consider the effect of proposals on the PaaS as a whole, including its frontend client, users, Azure hosting, ACA deployment workflow, and Clean Architecture boundaries.
- Do not infer specific Azure services, languages, frameworks, tenancy models, deployment flows, or security requirements unless the user or project documents establish them.
- Keep this instruction file focused on durable LLM guidance and technical conventions. Put product facts in the project brief.

- External SDK clients, credentials, and HTTP transports must be supplied to infrastructure providers as constructor dependencies. Construct clients in Nest module factories, register explicit tokens for interface dependencies, and avoid constructor fallbacks that create real clients. See `../provider-dependencies.md` for the current wiring.

- Deployment creation requires `Idempotency-Key`. Use the SQL-backed Nest HTTP store plus a deployment acceptance receipt written through the same application UnitOfWork as the deployment insert. Never separate the business receipt from that transaction or replay before authenticated/suspended-user guards. Dependency policies are supplied through the injected HTTP transport and Azure SDK pipeline; do not add nested retries around whole deployment/build workflows or retry pipeline submission. See `../reliability.md` for settings and guarantees.
- The GitHub webhook endpoint accepts only push events; reject other event types with HTTP 400 before processing. GitHub push processing must follow raw-body signature verification with `GITHUB_WEBHOOK_SECRET`. Scope candidate deployments by the signed repository owner's immutable GitHub ID, verify the current personal repository/app-installation owner through GitHub, and require the owner's DeploymentUpdate permission. Match the saved repository and branch, then reuse RedeployDeploymentCase for transactional receipt deduplication, subscription/quota checks, and queue acceptance. Never derive authorization or deduplication solely from unsigned event/delivery headers, or use the pusher's identity as the deployment owner. See `../github-webhooks.md` for behavior and current busy-app limitations.

- User creation and GitHub OAuth login must ensure an unlinked, unsuspended user has one Stripe Customer association in `users.stripe_customer_id`. Keep linking behind application ports, serialize user creation in the UoW, and keep network calls outside database transactions. The SQL-backed linking operation owns customer ID updates and uses one persisted Stripe idempotency key across retries/replicas. Do not rotate uncertain keys or bypass the 23-hour reconciliation guard. Normal user saves must preserve existing Stripe links. Session deserialization reloads the current user and active assigned-role grants with one joined SQL read and no UoW transaction; serialize only the user ID.
- Deployment API routes enforce permission grants before use cases, idempotency replay, and cached responses: creation requires DeploymentCreate; list/detail require DeploymentRead; start/stop require DeploymentUpdate; build status requires BuildRead; metrics require both DeploymentRead and DeploymentMetricsRead. Auth/profile and per-build source-token routes retain their existing authorization. Rename/delete use cases have no HTTP endpoints yet; apply their corresponding grants when exposing them. Roles are not automatically assigned.

- Database bootstrap data uses the standalone `npm run seed:db` command and infrastructure seed implementation. Preserve existing rows except ensure the admin role includes Super; require explicit user-role assignments and plan configuration. `npm run admin:add -- --github-id <numeric-id>` creates or promotes an administrator using the OAuth GitHub ID as users.id. This offline bootstrap may create an unlinked user; normal OAuth login establishes the Stripe Customer link afterward. Refuse inactive/suspended users and disabled admin roles. Bootstrap commands must not start the API or register subscriptions. See `../database-seeding.md`.
