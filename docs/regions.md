# Deployment region discovery

`GET /regions` requires an active, unsuspended authenticated session. It returns a list containing the configured shared managed environment's region, for example `[{ "name": "japaneast", "display_name": "Japan East" }]`. The example is illustrative; all actual values come from configuration and live Azure metadata. Region names are normalized and deduplicated.

The backend reads `AZURE_SHARED_ENVIRONMENT_NAME`, constructs its ARM ID from `AZURE_SUBSCRIPTION_ID` and `AZURE_PLATFORM_RESOURCE_GROUP` (falling back to `AZURE_RG_NAME`), then fetches that environment, subscription locations, Microsoft.App provider metadata, and the subscription's `sys.regionrestriction` assignment using the injected credential/HTTP transport. It requires a ready non-Express environment with an existing Consumption workload profile. It returns its region only when that region is a physical subscription location advertised for `Microsoft.App/containerApps` and permitted by the policy's live `listOfAllowedLocations`. A missing policy (404) or `DoNotEnforce` mode adds no restriction. A valid but empty intersection returns `[]`.

There are no managed environment count quota or VNet provider lookups. Full regional or global environment creation quotas do not hide the shared environment region because new apps reuse the environment. This lookup does not reserve CPU, replicas, subnet addresses, TCP ports, or any other environment capacity, and it does not evaluate general policies, initiatives, exclusions, or exemptions. Existing legacy apps may remain in a different region; the catalog describes the target for new apps.

No query parameters or subscription selectors are accepted (400). The scope is Kumo's backend-configured subscription, not a user-linked Azure account. There is no deployment permission or billing requirement. Responses use `Cache-Control: private, no-store` and are not cached. Missing or ineligible sessions return 403. Authentication, authorization, throttling, malformed metadata/policy, missing/unready environments, and other Azure failures return sanitized 503 errors rather than silently falling back to another region. Missing/invalid shared environment configuration fails during provider construction.

The backend identity needs `Microsoft.Resources/subscriptions/locations/read`, `Microsoft.Resources/subscriptions/providers/read`, `Microsoft.Authorization/policyAssignments/read`, and `Microsoft.App/managedEnvironments/read`. Deployment additionally needs permission to join the configured environment. `RegionsModule` uses the existing injected `AZURE_CREDENTIAL` and resilient `HTTP_TRANSPORT`. The listing shares a 30-second deadline and follows validated subscription-local location pagination; it never sends credentials to a pagination target outside the fixed ARM host and configured locations path.

Run `npm run test:api` for HTTP authorization/serialization and mocked shared-region discovery, scope, policy, pagination, and failure coverage. No test deploys resources to Azure.

References: [shared environment networking](user-networking.md), [subscription locations](https://learn.microsoft.com/en-us/rest/api/resources/subscriptions/list-locations), and [provider metadata](https://learn.microsoft.com/en-us/rest/api/resources/providers/get).

When the current disabled-by-default LegacyPerUserProvisioning feature flag is enabled, the region reader delegates to the preserved AzureLegacyDeploymentRegionsReader instead. That reader restores the original location/provider/policy intersection and per-region managed-environment count quota filtering. It has no effect while the flag is disabled or absent. The existing feature provider refreshes its snapshot every 12 hours; region lookup reevaluates the current snapshot on each call. See [legacy workflow](user-networking.md#preserved-legacy-workflow-disabled).
