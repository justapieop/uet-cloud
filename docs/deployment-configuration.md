# Applied deployment configuration

## Frontend resource editor preview

The deployment detail page offers **Edit** in **Compute & Scaling** for provisioned running/stopped deployments with complete applied resource values. It previews changes to per-replica CPU/RAM and minimum/maximum replicas, derives RAM using the established 1:2 CPU:memory ratio, and checks that the requested allocation fits one active plan. Plan lookup failures retain the draft and allow retry. Missing Azure values are not replaced with defaults.

Saving resource changes is not available yet. The frontend mutation adapter returns an explicit unavailable result, retains the draft, and leaves the displayed applied configuration unchanged. There is no resource-update endpoint behind this editor. Start/stop, redeploy, and volume operations keep their existing APIs. See the [frontend implementation notes](llm/deployment-spec-editor-plan.md) for the pending backend contract.

## Applied reads

`GET /deployments/:id` and `GET /deployments` read applied CPU, RAM, minimum/maximum replicas, primary/additional ports, ingress visibility (`external`), region, image, and FQDN from Azure Container Apps for deployments with an Azure resource ID. Database request values are not substituted for missing Azure fields or failed Azure reads. Missing optional Azure fields return null (or an empty additional-ports list). RAM is normalized to GiB and Azure location names to lowercase without whitespace.

The database continues to hold the creation request for durable queuing, provisioning, and quota reservations. Identity, ownership, build ID, Azure resource ID, workflow status, timestamps, and workflow errors remain database-backed. Existing image/FQDN columns are historical workflow snapshots; provisioned GET responses use Azure's values. This change introduces no destructive migration or removal of persisted requests.

Records without a resource ID that are pending, provisioning, or failed before app creation return submitted configuration. `DELETE_PENDING`, `DELETING`, `DELETE_FAILED`, and `DELETED` records return their saved snapshot without querying Azure because the resource may already be disappearing or gone. A running/stopped record without a resource ID is invalid and fails the read. Mutation responses and accepted idempotency replays still represent their saved request/operation receipt, rather than issuing an additional cloud lookup.

`DELETE /deployments/:id` is an owner-scoped asynchronous request and returns HTTP 202 with no response body. The caller must have both DeploymentDelete and DeploymentRead; Super does not bypass the ownership check. Deletion does not require an active Stripe subscription, so a user can clean up resources after a plan expires. Follow progress through the owner-scoped detail/list endpoints. Repeating the request while deletion is pending or running is safe; retrying `DELETE_FAILED` queues another attempt. Requests that race with provisioning or start/stop operations return HTTP 409. The saved Azure resource ID remains historical metadata even after deletion; the deployment slot is released when `container_app_deleted_at` is recorded after confirming the app is absent.

Ownership is checked in the application layer before calling the infrastructure reader. The reader validates that the saved ARM resource ID belongs to the configured subscription and the user's `user-rg-<id>`, rejects the platform resource group, and verifies the returned app ID and `kumo-deployment-id` tag. It selects the container matching the app name, or the only container when there is exactly one. Azure SDK models stay in infrastructure; an application port supplies the read projection to presentation, without mutating or persisting it on the deployment domain.

List reads resolve at most four apps concurrently, with a 15-second timeout per ARM request. Region filters apply to the resolved Azure region for provisioned apps, and to the requested region before provisioning. Other filters continue to use database workflow fields. If any cloud lookup fails, the list fails rather than silently omitting that deployment. Azure missing/invalid/inaccessible resources return HTTP 502; transient failures and throttling return 503. Missing or foreign-owned database records remain 404. Existing resilience error handling is preserved.

The opt-in response cache uses two seconds for pending/provisioning or mixed-state deployment results and ten seconds for running/stopped results. Permissions run before cache hits; bypass directives still force a fresh lookup. No Azure call or cloud wait occurs inside a database transaction. Reads do not reconcile Azure drift into saved quota reservations or enforce subscription quotas against manual changes made outside Kumo. See [database load](database-load.md) for scheduling, authorization, and caching guarantees.

## Deletion recovery and persistence

Deletion accepts `PENDING`, `RUNNING`, `STOPPED`, `FAILED`, and retries from `DELETE_FAILED`. It persists `DELETE_PENDING`; the worker claims that row as `DELETING` and assigns a fresh internal UUID in `deletion_claim_token`. Every deletion progress write must match the owner, deployment ID, `DELETING` status, and that token. Recovering a stale job clears the token before requeuing it, so the previous worker cannot overwrite progress from the replacement worker. Provisioning progress writes also require the row to remain `PROVISIONING`, preventing a late result from overwriting deletion states. The token is not returned by the API.

The worker checks stale jobs once per minute when it is available, using `AZURE_DEPLOYMENT_TIMEOUT_MS` plus one minute as the cutoff. Interrupted `DELETING` work is automatically requeued; `DELETE_FAILED` requires another DELETE request. If the app has already been confirmed absent, retries retain `container_app_deleted_at` and continue storage-link cleanup without deleting the app again. Storage-link failure after that point does not reserve a deployment slot. Azure File shares, volume records/data, resource groups, and managed environments are retained. A `DELETED` row remains readable and listable, and its globally unique name remains reserved.

The migrations `DeploymentDeletion1793232000000` and `DeploymentDeletionClaims1793836800000` add cleanup checkpoints, operation leases, and the claim token without rewriting creation requests. Existing records start with a null token and acquire one when a pending deletion is claimed. Apply migrations before running the updated workers; the API's existing startup migration mechanism registers both. Compilation does not apply migrations. Stop API replicas before rolling the token migration back, since the updated repository requires its column.

These conditions protect SQL workflow updates. They do not cancel an Azure operation already accepted by Azure when a process stops or a request times out. A recovered attempt can repeat cloud cleanup; the adapter revalidates ownership and treats resource absence as success. General reconciliation of out-of-band Azure changes or late provisioning remains a separate follow-up.
