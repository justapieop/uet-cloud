# Shared workload environment and networking

In default shared mode, all new user Container Apps reuse the existing managed environment configured by `AZURE_SHARED_ENVIRONMENT_NAME`. Supply its name through backend `.env`, deployment environment variables, or Azure App Configuration. Kumo constructs its ARM ID using `AZURE_SUBSCRIPTION_ID` and `AZURE_PLATFORM_RESOURCE_GROUP` (falling back to `AZURE_RG_NAME`). The environment must be in that group. Its region and Consumption workload profile name are read from Azure.

Kumo reads the environment and verifies its identity, location, readiness, and existing Consumption workload profile. It rejects Express mode and waits within the operation deadline for an environment that is still provisioning. Missing, failed, or incompatible environments stop the deployment before user resource-group creation or image building. Kumo never creates, updates, deletes, or repairs managed environments, VNets, or subnets during workload provisioning. Environment/network changes are a separate operator responsibility.

Container Apps remain in `user-rg-<userId>` with the existing numeric GitHub ID validation, resource-ID checks, and deployment ownership tags. A user resource group is created as needed in the shared environment's normalized region. Existing groups are preserved; their metadata location need not equal the app's location. Platform resource-group mutation remains forbidden: reading and joining its explicitly configured environment does not authorize creating apps or changing its network there.

Users may omit `region` or supply the shared environment's region. A different requested region fails before provisioning or building. `GET /regions` advertises only the configured environment region when allowed by the current subscription policy and advertised Container Apps support. It does not hide that region when managed environment creation quota is exhausted because no environment is created.

Existing apps retain their current environment on reuse or image-only redeployment. Besides the configured shared environment, Kumo permits only the legacy `user-aca-env-<userId>` inside that same user's group and subscription. It does not move apps, recreate missing legacy environments, or adopt another user's environment. Changing the configured shared name or platform resource group affects new apps; migrating existing apps remains separate work.

## Accepted isolation model

Users accepted a shared environment, including shared networking with any platform apps hosted there. Resource groups and application authorization preserve management ownership; they do not provide tenant network isolation. Internal ingress (`external: false`) and internal TCP mappings are reachable by other apps in the shared environment, including other users' apps. Do not describe this as user-private networking. CPU/RAM, replica, subscription, and ownership admission checks remain in place, while environment-wide capacity is shared. Keep per-app secrets and identities scoped to their intended app; the ACR pull identity retains lifecycle `None`.

External additional TCP mappings still require a VNet-connected environment, verified from its existing `infrastructureSubnetId`. If absent, fail before building rather than modifying the environment. Exposed external ports must be unique across the shared environment; Azure arbitrates conflicts. Dapr components, storage mounts, environment certificates, and network changes are not created by this switch.

Reference: [Microsoft's Container Apps multitenancy guidance](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/service/container-apps).

## Preserved legacy workflow (disabled)

The old resource-group → per-user VNet/delegated subnet → per-user Workload Profiles environment → successful build → app workflow remains in `AzureLegacyEnvironmentProvisioner`. It is controlled by the disabled-by-default Azure App Configuration boolean feature flag `LegacyPerUserProvisioning`. A missing flag also selects shared mode; there is no environment-variable override. Shared-mode errors never trigger it as a fallback. The network SDK client and writable environment adapter are created lazily on the first operation that observes the flag enabled; direct calls to the legacy adapter also reject when disabled.

For a future deliberate re-enable, enable the unconditional `LegacyPerUserProvisioning` flag in Azure App Configuration Feature manager. Do not configure targeting, percentages, schedules, variants, or other conditions for this platform-wide switch; these are treated as disabled. New apps then use the per-user workflow. Set `AZURE_LEGACY_DEFAULT_REGION` for requests that omit a region and need a new user resource group; there is no hardcoded location fallback. Explicit request regions and an existing group's normalized location retain the old behavior. Existing apps still retain their applied environment. Keep the shared name and platform resource group configured so the API can validate existing shared apps and switch back to shared mode after refresh.

The preserved implementation creates `user-rg-<userId>`, `user-vnet-<userId>`, and `user-aca-env-<userId>` with the original naming and isolation checks. New VNets use `10.0.0.0/16` and a dedicated `aca-infrastructure` subnet at `10.0.0.0/24` delegated to `Microsoft.App/environments`. It awaits network/subnet readiness before environment creation, then awaits the environment before the existing build/app flow. Only 404 means missing; incompatible networks and authorization errors stop provisioning without overwriting resources. Redeployment never recreates a missing environment. This mode needs the previous environment, network, subnet, and user-resource-group write/join permissions, and remains subject to global environment limits.

The region catalog also switches explicitly to the preserved subscription-location/provider/policy/quota intersection in legacy mode. Shared mode keeps the existing-environment single-region catalog and ignores environment-count quotas.

Provisioning and region discovery evaluate the current FeatureFlagsService snapshot at the start of each operation. The existing Azure feature-flag polling interval is 12 hours; changes apply after a successful refresh or API restart. Refresh failures retain the last known snapshot. Work already in progress is not migrated or cancelled. With CONFIG_SOURCE=local, the flag list is empty and legacy remains disabled.
