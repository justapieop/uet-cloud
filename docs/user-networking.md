# User workload networking

Before creating a missing `user-aca-env-<userId>`, Kumo creates or reuses `user-vnet-<userId>` inside the same `user-rg-<userId>`. Both use the requested region or, when omitted, the resource group's normalized location.

New VNets use address space `10.0.0.0/16` and include an `aca-infrastructure` subnet at `10.0.0.0/24`, delegated to `Microsoft.App/environments`. These are implementation defaults for isolated, unpeered user VNets, not client request fields. Future peering or private-network connectivity needs a separate address-allocation design.

Provisioning order is resource group → VNet with delegated subnet → managed environment → successful image build → Container App. Kumo waits for the network creation poller, validates network and subnet readiness, then supplies the subnet's resource ID through `vnetConfiguration.infrastructureSubnetId`. `internal: false` retains an external environment. Workload Profiles with the Consumption profile and private ACR image pulls remain in effect.

Only a 404 triggers creation. Other lookup errors stop provisioning. Existing VNets are never overwritten; reuse requires matching subscription, user resource group, name, and region, plus a ready `aca-infrastructure` subnet delegated to `Microsoft.App/environments` with an IPv4 prefix of /27 or larger. An incompatible or incomplete existing network fails with an actionable message. Network failures prevent environment creation and build submission. Network operations use the deployment abort/deadline and the shared ARM resilience policy. Successfully created networking remains after a later failure for reuse.

Existing managed environments are reused without network mutation, VNet creation, deletion, or replacement. Azure cannot change an environment's network type after creation. Existing environments without VNet integration can still run HTTPS/internal additional ports, but external additional TCP ports continue failing before a build and require a separately planned environment migration. New environments receive VNet integration automatically. External port uniqueness across the shared environment is still enforced by Azure.

The presentation `DeploymentModule` constructs `NetworkManagementClient` using the existing `AZURE_SUBSCRIPTION_ID` and injected Azure credential, with SDK retries disabled and the shared ARM pipeline policy. Infrastructure receives its virtual-network operations through `AzureProviderClients`; no extra network credentials or configuration keys are needed. The API identity requires `Microsoft.Network/virtualNetworks/read`, `Microsoft.Network/virtualNetworks/write`, subnet read/write, and subnet join permissions in user resource groups, in addition to its existing provisioning permissions. The subscription must have the relevant network resource provider registered.

Run `npm run test:api` for mocked provisioning order, readiness, reuse, region, isolation, failure, and external-port regressions. Source changes and compilation do not provision Azure resources. Live network creation, RBAC, and public TCP reachability require a configured Azure environment and are not established by these tests.

References: [Azure subnet requirements](https://learn.microsoft.com/en-us/azure/container-apps/custom-virtual-networks?tabs=workload-profiles-env), [environment network immutability](https://learn.microsoft.com/en-us/azure/container-apps/networking#virtual-network-type), and [additional TCP ports](https://learn.microsoft.com/en-us/azure/container-apps/ingress#additional-tcp-ports).
